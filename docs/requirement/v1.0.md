# 프로젝트 구상 v1.0

# 1. 문제 정의 및 목표 설정

## 프로젝트 개요

- **프로젝트명:** 선착순 쿠폰 발급 시스템
- **목표:** 선착순 쿠폰 발급에서 트래픽이 몰렸을 때 발생하는 정합성·성능 문제를 직접 경험하고, 점진적으로 개선하며 학습한다.

## 배경 및 필요성

- **선착순 쿠폰 이벤트의 특성**
    - 이벤트 오픈 시점에 짧은 시간 동안 대량 트래픽이 집중된다.
    - 쿠폰 수량은 한정되어 있어 정확한 재고 관리가 필수다.
    - 한 유저가 같은 쿠폰을 중복 발급받으면 안 된다.
- **단순 구현 시 발생하는 문제들**
    - 동시 요청 시 재고 수량이 맞지 않는다 (lost update).
    - 트랜잭션 내 외부 API 호출로 DB 커넥션이 고갈된다.
    - JVM 레벨 동기화(synchronized)로는 다중 서버 환경에서 정합성을 보장할 수 없다.
- **학습 방향**
    - 처음부터 완벽한 설계를 하지 않는다.
    - 간단한 구현에서 시작해 문제를 직접 확인하고, 원인을 분석한 뒤 개선한다.

# 2. 요구사항 분석

## (1) 핵심 도메인

이 프로젝트의 학습 포커스는 **쿠폰 발급 시 동시성·성능 문제 해결**이다. 유저 생성, 포인트 충전, 쿠폰 생성 등 셋업 API는 부하 테스트 편의를 위해 제공하되, 동시 트래픽이 몰리는 지점은 쿠폰 발급 엔드포인트 하나다.

## (2) 셋업 API (부하 테스트용)

- **유저 생성**: 이메일, 이름으로 유저를 생성한다.
- **포인트 충전**: 유저의 포인트를 충전한다.
- **쿠폰 생성**: 이름, 설명, 포인트 비용, 총 수량, 시작/종료일을 지정하여 쿠폰을 생성한다.

> 순차 호출로 테스트 데이터를 준비하는 용도. 동시성 문제와 무관.

## (3) 쿠폰 발급 요건 (핵심)

- 유저가 포인트를 차감하고 선착순 쿠폰을 발급받는다.
- **중복 발급 불가**: 같은 유저가 같은 쿠폰을 2번 받을 수 없다 (1인 1매).
- **재고 차감**: 발급 시 `remainingQuantity`를 1 감소시킨다. 0이면 발급 거부.
- **기간 검증**: 현재 시각이 `startDate ~ endDate` 범위 안이어야 발급 가능.
- **포인트 차감**: 유저 잔액이 `pointCost` 이상이어야 하며, 발급 시 차감한다.
- **알림 전송**: 발급 성공 시 외부 알림 서버로 푸시 알림을 전송한다.

## (4) 상태/라이프사이클

### Coupon 가용 여부

쿠폰 자체에 상태 필드를 두지 않고, 아래 조건으로 판단한다.

- **발급 가능**: `remainingQuantity > 0` AND 현재 시각이 `startDate ~ endDate` 범위 안
- **품절**: `remainingQuantity == 0`
- **기간 만료**: 현재 시각이 `endDate` 이후

### CouponIssue 상태

- `ISSUED` — 발급 완료
- `USED` — 사용 완료
- `EXPIRED` — 만료

> v1.0에서는 `ISSUED` 상태만 사용한다. `USED`, `EXPIRED` 전환은 이후 버전에서 다룬다.

# 3. 제약 사항

- HikariCP 풀 사이즈 10 고정 (변경 금지)
- DB는 H2만 사용 (tcp 모드, 서버 간 공유)
- 쿠폰 서버는 2대 구성 유지
- 컨트롤러 URL, HTTP 메서드, 요청/응답 필드 변경 금지
- 알림 mock 서버는 2~3초 지연을 시뮬레이션

# 4. 데이터 설계 (요약)

| 엔티티 | 주요 필드 | 비고 |
|--------|----------|------|
| User | id, email, name, point | 사전 적재, 포인트 보유 |
| Coupon | id, name, description, pointCost, totalQuantity, remainingQuantity, startDate, endDate | 사전 적재, 재고 관리 |
| CouponIssue | id, userId, couponId, status, issuedAt | 발급 이력, 중복 방지 |

### 관계

- User `1` — `N` CouponIssue
- Coupon `1` — `N` CouponIssue

> 상세 엔티티 설계는 `docs/design/entity/v1.0.md`에서 정의한다.

# 5. 비기능 요구사항

- **정합성**: 200명 동시 발급 요청 시 재고 == 실제 발급 건수가 정확히 일치해야 한다.
- **성능**: 200명 동시 요청을 10초 이내에 처리해야 한다.
- **안정성**: DB 커넥션 풀(10개)이 고갈되지 않아야 한다.
- **분산 환경**: 두 대의 서버에서 동시에 요청해도 초과 발급이 발생하지 않아야 한다.

# 6. 점진적 개선 로드맵

## Phase 1 — 기본 기능 구현

> "일단 돌아가게 만든다"

- 엔티티(User, Coupon, CouponIssue) 설계 및 구현
- 셋업 API 구현 (유저 생성, 포인트 충전, 쿠폰 생성)
- 쿠폰 발급 API 구현 (검증 → 포인트 차감 → 재고 차감 → 발급 이력 저장 → 알림)
- 알림 서버 연동 (트랜잭션 내 동기 호출)
- **예상 문제**: 단일 요청은 정상 동작하지만, 동시 요청 시 재고 불일치 및 커넥션 고갈 발생

## Phase 2 — 동시성 문제 해결

> "200명이 동시에 눌러도 재고가 정확해야 한다"

- 학습 주제: lost update, race condition, DB 락 전략
- 비관적 락 또는 원자적 UPDATE로 재고 차감의 정합성 확보
- 중복 발급 방지 강화
- **검증**: 부하 테스트(200 concurrent)에서 `totalQuantity - remainingQuantity == 발급 건수`

## Phase 3 — 커넥션 고갈 해결

> "외부 호출이 느려도 서비스는 죽지 않아야 한다"

- 학습 주제: 트랜잭션 범위, 커넥션 점유 시간, 이벤트 기반 처리
- 트랜잭션 내 외부 API 호출(알림)을 트랜잭션 밖으로 분리
- 커넥션 점유 시간 최소화
- **검증**: 알림 서버 지연(2~3초)이 있어도 발급 처리 정상, 커넥션 풀 고갈 없음
