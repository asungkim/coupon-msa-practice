## 2. 도메인 변경

### 2.1 신규 엔티티 (초기 구축)

- **User**: id, email, name, point
- **Coupon**: id, name, description, pointCost, totalQuantity, remainingQuantity, startDate, endDate
- **CouponIssue**: id, userId, couponId, status(IssueStatus), issuedAt
    - UNIQUE 제약: (userId, couponId)

### 2.2 Enum

```java
enum IssueStatus {
    ISSUED,   // 발급 완료
    USED,     // 사용 완료 (v1.0 미사용)
    EXPIRED   // 만료 (v1.0 미사용)
}
```

> 상세 필드 정의는 `docs/design/entity/v1.0.md` 참조

## 3. 비즈니스 규칙

### 3.1 쿠폰 발급 검증 (순서대로)

1. **중복 발급 검사**: userId + couponId로 기존 발급 이력 존재 시 거부
2. **유저 존재 검사**: userId에 해당하는 유저가 없으면 거부
3. **쿠폰 존재 검사**: couponId에 해당하는 쿠폰이 없으면 거부
4. **발급 가능 검사**: `remainingQuantity > 0` AND 현재 시각 ∈ `[startDate, endDate]`
5. **포인트 잔액 검사**: `user.point >= coupon.pointCost`

### 3.2 쿠폰 발급 처리 (순서대로)

1. 유저 포인트 차감 (`user.point -= coupon.pointCost`)
2. 쿠폰 재고 차감 (`coupon.remainingQuantity--`)
3. CouponIssue 생성 (status = ISSUED)
4. 알림 서버로 푸시 전송

### 3.3 포인트 규칙

- 포인트는 0 미만이 될 수 없다
- 충전 시 기존 포인트에 누적

## 4. API 설계

### 4.1 셋업 API

| Method | Endpoint | 설명 |
|--------|----------|------|
| POST | `/api/users` | 유저 생성 |
| POST | `/api/users/{userId}/points` | 포인트 충전 |
| POST | `/api/coupons` | 쿠폰 생성 |

#### POST `/api/users`

```
Request:  { "email": "test@test.com", "name": "홍길동" }
Response: { "id": 1, "email": "test@test.com", "name": "홍길동", "point": 0 }
```

#### POST `/api/users/{userId}/points`

```
Request:  { "amount": 10000 }
Response: { "id": 1, "email": "test@test.com", "name": "홍길동", "point": 10000 }
```

#### POST `/api/coupons`

```
Request:  {
    "name": "대박쿠폰",
    "description": "이벤트 오픈 기념",
    "pointCost": 100,
    "totalQuantity": 200,
    "startDate": "2026-04-14T00:00:00",
    "endDate": "2026-05-14T00:00:00"
}
Response: {
    "id": 1,
    "name": "대박쿠폰",
    "description": "이벤트 오픈 기념",
    "pointCost": 100,
    "totalQuantity": 200,
    "remainingQuantity": 200,
    "startDate": "2026-04-14T00:00:00",
    "endDate": "2026-05-14T00:00:00"
}
```

### 4.2 쿠폰 발급 API (핵심)

| Method | Endpoint | 설명 |
|--------|----------|------|
| POST | `/api/coupons/{couponId}/issue` | 쿠폰 발급 요청 |

#### POST `/api/coupons/{couponId}/issue`

## 5. 에러 케이스

| 상황 | HTTP Status | 에러 메시지 |
|------|-------------|------------|
| 유저 미존재 | 404 | User not found |
| 쿠폰 미존재 | 404 | Coupon not found |
| 중복 발급 | 409 | Coupon already issued to this user |
| 재고 소진 | 409 | Coupon out of stock |
| 기간 외 발급 | 400 | Coupon is not available or expired |
| 포인트 부족 | 400 | Insufficient points |

## 6. 구현 참고사항

### 트랜잭션 범위

- Phase 1에서는 쿠폰 발급의 전체 흐름(검증 → 차감 → 저장 → 알림)을 **하나의 `@Transactional`**로 처리한다.
- 이는 의도적으로 문제가 있는 구현이다: 알림 서버 호출(2~3초)이 트랜잭션 안에서 동기 실행되어 DB 커넥션을 오래 점유한다.
- Phase 3에서 알림을 트랜잭션 밖으로 분리하며 해결한다.

### 동시성 제어

- Phase 1에서는 `coupon.remainingQuantity--`를 Java 레벨에서 처리한다 (단순 엔티티 필드 감소).
- 이는 의도적으로 문제가 있는 구현이다: 동시 요청 시 lost update가 발생한다.
- Phase 2에서 DB 레벨 락(비관적 락 또는 원자적 UPDATE)으로 해결한다.

### 알림 연동

- `PushNotificationClient`가 WebClient로 notification-mock-api(`localhost:8090`)에 동기 호출한다.
- mock 서버는 2~3초 지연 후 `{ success: true, messageId: UUID }` 반환한다.
- 알림 실패 시에도 쿠폰 발급 자체는 롤백하지 않는다 (Phase 3에서 이벤트 분리 후 자연스럽게 해결).

### Phase별 변경 예고

| Phase | 변경 대상 | 현재 (Phase 1) | 개선 후 |
|-------|----------|---------------|---------|
| 2 | 재고 차감 | Java `remainingQuantity--` | DB 비관적 락 or 원자적 UPDATE |
| 2 | 중복 방지 | `existsByUserIdAndCouponId` 조회 | + UNIQUE 제약 DB 레벨 보장 |
| 3 | 알림 호출 | 트랜잭션 내 동기 호출 | 트랜잭션 밖 이벤트 기반 비동기 |
